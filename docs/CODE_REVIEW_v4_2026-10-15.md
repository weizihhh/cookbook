## 2. v0.18.0 评审:目标体重与进度预测

### 2.1 设计回顾【代码事实】

- 理论轨:`theoryProgress(tdee, kcal, currentWeight, targetWeight)`(`nutrition.js`),缺口 `tdee - kcal`,
  周速率 `-(gap×7)/7700`,到日 `ceil(|remaining|×7700/|gap|)`。三个 null 出口:缺口 <1kcal、已达标、
  方向相反(缺口与剩余量异号)。
- 实测轨:`measuredWeeklyRate(records, today, 28)`——近 28 天窗口内 ≥2 条且首尾跨度 ≥14 天,
  速率 = (尾-首)×7/跨度;不满足返回 null(不显示)。
- 呈现(`RecordView.vue` progressInfo):
  - 维持模式整块不渲染;未设目标体重渲染引导 placeholder;
  - 起点 `weight.recentAvg7 ?? profile.weight`;
  - 减脂:理论行 + 实测行,`|实测/理论 - 1| > 0.5` 时出"偏差较大"hint;
  - 增肌:只显示周增速并对照 +0.25~0.5kg/周建议区间,**不预测到日**(决策见 DECISIONS.md:v0.18.0);
  - 底部免责:"起点按近 7 天均值 · 7700kcal≈1kg 估算,仅供参考"。
- verify §24 覆盖:缺口 500 → -0.45kg/周/154 天;增肌盈余 280 → +0.25kg/周;三个 null 场景;窗口与跨度边界。

### 2.2 评审结论

**设计评价:良好。** 三条边界处理(方向相反/已达标/缺口≈0)都返回 null 而非异常值,实测轨用
"跨度≥14 天"防止两条相邻记录放大噪声,双轨偏差 >50% 出提示而不是断言谁对——符合"记录型工具给参考、
不给判决"的定位。增肌不预测到日是有据取舍(盈余在肌肉/脂肪间的分区个体差异大),已登记 DECISIONS.md。

**发现的问题:**

- **F-2.1【代码事实,低】起点与 TDEE 存在 ≤2kg 的口径差。** TDEE 来自 `profile.targets`,
  其体重经 `effectiveWeight` 2kg 步进(v0.16.0 半动态,朝档案体重保守);而进度起点用 `recentAvg7` 原始均值。
  两者最大差 1.99kg → TDEE 差约 20~30kcal/天,相对于缺口 300~500kcal/天误差 <10%,且页面有免责说明。
  定性:双保守设计叠加的可接受近似,**不建议改**(把 recentAvg7 直接喂进 TDEE 会重新引入逐日噪音,
  正是 v0.16.0 要避免的)。
- **F-2.2【推断,低】远期到日有"假精确"观感。** 20kg 剩余 + 500kcal 缺口 → 308 天后一个具体日期。
  但 7700kcal/kg 本身 ±20% 个体差、TDEE 随减重下降(平台期),具体日期必然失真。
  已有缓解:免责 note + 实测轨对照。可选项(非建议,记录备查):剩余量 >10kg 时只显示"约 N 个月"。
  鉴于自用工具 + 已有双重缓解,**维持现状即可**。

**未发现逻辑错误。** §24 断言绑定具体期望值,方向(减负重 weeklyKg<0、增肌 >0)经回读源码确认无误。

## 3. v0.19.0 评审:食材频次约束

### 3.1 设计回顾【代码事实】

- 数据:`weeklyLimit` 三条——猪肝 1、鸡肝 1、金枪鱼(罐头)2(`foods.js`)。
- 计数:`recentFoodDays(days, today, 7)`——滚动 7 天、按天去重(同天多餐计 1),生成与手动记录同口径。
- 硬规避:`assembleMeal` 三处候选过滤 + `swapSlotItem` 过滤,`overLimit` 即 `count >= weeklyLimit`;
  **不参与池空回退**(宁可空槽也不超限)。
- 跨天:`generateWeekPlan` 每天生成后把当天食材 `counts[id] += 1`,周内累计生效。
- 软提示:`weeklyLimitHits` 在添加确认层提示(红字、不阻断);LibraryView 食材行标 `· 建议 ≤N 次/周`。
- verify §25:计数口径、生成规避(随机 5 次)、换菜规避(随机 10 次)、**对照组**(临时摘除
  `f_pork_liver.weeklyLimit` 验证约束确在起作用,随后还原)、软提示三场景。

### 3.2 评审结论

**设计评价:良好,取舍清晰。** "硬规避不进回退 + 软提示不阻断"的双层结构正确地区分了
"生成替你负责"与"手动你自己负责"。对照组断言(摘掉限制看行为变化)是本轮自检里最扎实的一条——
它测的是约束生效而非约束存在。

**发现的问题:**

- **F-3.1【代码事实,低,实际不可达】天内不累计。** `generateDayPlan` 将同一份 `foodDayCounts`
  传给三餐,天内新生成的餐不更新计数——理论上同一受限食材可出现在同一天午餐+晚餐。
  **但本轮核实:三个受限食材各自只出现在 ≤1 个食谱中**(猪肝:`r_stir_fried_pork_liver`;
  金枪鱼:`r_tuna_salad`),而 `usedIds` 阻止同食谱天内重复,故"同食材同天双 pick"
  在当前库结构下**构造不出来**。该问题仅在"将来某受限食材进入 ≥2 个食谱"时激活。
  建议(可选,非阻塞):在 `foods.js` 头部注释补一句"同一受限食材入多个食谱前,需先解决
  generateDayPlan 天内累计"。
- **F-3.2【代码事实,提示】鸡肝的 weeklyLimit 当前是死配置。** `f_chicken_liver` 不属于任何食谱
  (全库 grep 仅 foods.js 一条),生成层与软提示层(基于添加项的 ingredients)都永远触不到它。
  它唯一的生效路径是将来鸡肝入食谱。定性:**无害的前瞻配置**,但 verify 没有断言"每条
  weeklyLimit 至少被一个食谱引用",无法防"配置了却永远哑火"。可选:加一条 verify 断言
  (受限食材必须有 ≥1 食谱引用,否则提示去补食谱)。是否要做由你定,做则属"数据完备性"性质。
- **F-3.3【代码事实,低】重新生成时旧计划内容也计入频次。** `week.generateDay` 中
  `recentFoodDays(this.days, date)` 在 `this.days[date]` 被覆盖**之前**求值,将被弃掉的旧计划
  也算进 7 天计数。效果:若旧计划含猪肝,重新生成当天会规避猪肝(保守方向)。
  定性:方向安全(只多避不少避),语义略意外。鉴于受限食材极少,实际影响≈0;**不建议改**,
  在此记录语义即可。

**未发现逻辑错误。** `overLimit` 的 `>=` 边界(计数已达上限即规避)与 `weeklyLimitHits`
的命中条件经回读一致;DECISIONS.md 已登记"同天多餐算 1 天"口径。

## 4. v0.20.0 评审:PWA

### 4.1 设计回顾【代码事实】

- 手写零依赖 SW(`public/sw.js`,68 行):导航 network-first(断网回退缓存壳)、
  静态资源 cache-first(命中即返回,未命中回源后写缓存)、预缓存壳+图标、`skipWaiting` +
  `clients.claim` + activate 清旧缓存。
- manifest:standalone、薄荷主题色 #00b578(顺带修掉 index.html 残留的 Vant 旧蓝 #1989fa)、
  192/512/maskable 三规格图标;index.html 补 iOS 安装元信息(apple-touch-icon 等)。
- 图标:`scripts/make-icons.mjs` 纯 Node 手写 PNG 编码 + SDF 绘制,零依赖、参数化可复跑。
- 注册:`main.js` 仅 `import.meta.env.PROD` 注册,dev 不受影响。
- verify §26:manifest 字段、图标文件存在且为有效 PNG(magic bytes)、sw.js 关键策略字符串、
  index.html 元信息,共 6 条。

### 4.2 评审结论

**设计评价:好,范围控制得当。** 手写 SW 对"壳离线"这个需求是合理最小解(Workbox 对单页纯前端
是过度工程);network-first 导航 + cache-first 哈希静态资源是标准正确策略;仅生产注册避免了
dev HMR 缓存地狱。图标生成脚本可复跑、可改参,优于二进制资产进库。

**发现的问题:**

- **F-4.1【代码事实,低】缓存版本号靠手动 bump。** sw.js 注释要求"发新版改 CACHE 版本号",
  但哈希文件名的 js/css 内容寻址、新版文件名不同,旧缓存不 bump 也能拿到新代码;
  真正依赖 bump 的只有"清理旧缓存条目"。忘记 bump 的后果是旧哈希资产永久滞留(单机几 MB 量级),
  不是正确性问题。定性:可接受的运维约定,与"有内容的天永不清理"同属知情取舍。
- **F-4.2【代码事实,提示】SW 行为只靠字符串包含断言。** §26 检查 `sw.js` 包含
  `request.mode === 'navigate'` 等字符串——防的是"文件被整体删改",防不了策略逻辑写错。
  但 SW 逻辑的正确性只能在浏览器/preview 环境实测(commit message 记录已实测 SW 激活与
  14 条资产缓存),Node 侧无法更深。定性:自检深度已达该层级的合理上限。
- **F-4.3【代码事实,已知取舍】OCR 语言包离线不可用。** CDN 跨域不缓存,断网时拍照导入退化为
  手动录入。已登记 DECISIONS.md,自托管语言包是独立候选轮次。**不再展开。**
- **F-4.4【提示】`skipWaiting` + `clients.claim` 立即接管。** 用户开着旧页面时新 SW 直接生效,
  旧页面持有的已加载资源不受影响(纯前端、无服务端会话),下一次导航即新版。对本应用无风险,
  记录备查。

**未发现逻辑错误。**
