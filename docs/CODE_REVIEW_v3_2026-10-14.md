**E1 的独立复核(我做了,结论支持用户)**

用户指出 24.7g 碳水配 61kcal 物理上不可能。我做了两项独立验证:

1. **算术**:`24.7 × 4 = 98.8` kcal(仅碳水)已 **> 61**;再加 P1.1×4 + F0.2×9 = 6.2 → **105.0** kcal。故该条目能量不可能小于 98.8。
2. **质量平衡**:官方页 水 73.4 + P 1.1 + F 0.2 + 灰分 0.6 + 碳水 24.7 = **100.0g 精确闭合**。若碳水按 15.3 计,只到 90.6g,**缺 9.4g 无解释**。→ 充分说明 73.4 的水分是配 24.7 碳水的。

**关于"61kcal"的来历(修正我原先的定性)**:我原来把它称为"污染",不够准确。联网检索显示 61kcal 不是随机噪声,而是**被长期、大规模传播的旧数据** —— 浙江省市场监督管理局的消费提示、人民日报的科普文章都写"红心红薯 61kcal/100g",部分文章还把它挂在"第6版"名下。所以更准确的说法是:**它是一个流通极广、与同条目碳水值自相矛盾、且被误挂到现行版名下的旧值**。这解释了它为什么会反复出现在搜索摘要里,也说明**不能靠"搜索摘要多个来源一致"来采信** —— 一致的错误比随机错误更容易骗过评审。

**结论**:项目改 90 → 103 / C21.3 → 24.7 是**正确且必要的**;v3 原文的克制("不作错误判定")形式上对、方向上错 —— 真正的教训是:**"不确定"不等于"两边都有可能",当一边存在硬约束(算术/质量平衡)时,应该用硬约束把它判掉,而不是并列悬置。**

  1. 用合成数据去撞 `dev < -0.12 || dev > 0.5`,测的是**检查器自身**,是恒真的自证;
  2. 对**数据**做一次性变异(把蒜薹改回 8.0 看它红不红),其价值已被**锚点断言完全覆盖** —— 锚点("蒜薹 150g = 23.1g 碳水")在构造上就会因 8.0 而失败,且每次运行都在守着,严格优于一次性手动变异;

- **观点(事实性残留)**:闸门 + 锚点都无法拦住"**新增一行**在 `[-12%, +50%]` 内、且未被锚定的错值"。这是锚点机制的固有边界(锚点只覆盖被显式写明的条目),不是可修补的缺陷;接受它。

```js
// week.js
summaryOf(date) { ... return summarizePlanned({ date, meals }, FOODS_MAP, profile.targets) }

// TodayView.vue:253
const summary = computed(() => (todayMeals.value ? week.summaryOf(today.value) : null))
// 266:  if (!summary.value || !hasAnyItem.value) return 'none'
```

`summary.value` 的 `.totals` / `.diff` **从未被读取**;仅用其**真值性**。

**两点补充(比"返回值没人用"更具体)**:

1. **真值性完全等价于已有变量**:`summaryOf` 当且仅当 `days[date]` 不存在时返回 null,所以 `summary.value` 的真值 ≡ `todayMeals.value` 的真值 ≡(`hasAnyItem` 为真时必然为真)。两处 `summary.value` 检查在 `!hasAnyItem.value` 已存在的前提下**是冗余的**。

**建议(用户已列为"下次清理候选",我同意)**:`summary` computed 可直接删除,两处改用 `hasAnyItem.value` / `todayMeals.value`;`week.summaryOf` 随之成为无调用方的 getter,可一并移除。**纯清理,零行为变化,无发布价值,适合并入下一次功能改动的顺手清理。**
