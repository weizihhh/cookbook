## 2. 食谱库数据准确性

### 2.1 已修复的 4 条错误(v0.16.3)

| 食材 | v0.16.2(错) | v0.16.3(对) | 错误性质 | 来源核对 |
|---|---|---|---|---|
| 鸡胸肉 | P**22.0** / C**0** | P**19.4** / C**2.5** | 跨来源缝合(能量取中国表、宏量取另一套) | 第 6 版 鸡胸脯肉:133kcal / P19.4 / C2.5 / F5.0 / 食部100% |
| 燕麦片 | **338** kcal / C**61.0** | **381** kcal / C**66.9** | 能量误用"燕麦粒"条目 | 第 6 版 燕麦片:1593kJ(381kcal) / P15.0 / C66.9 / F6.7 |
| 蒜薹 | C**8.0** | C**15.4** | 碳水误用"蒜苗"条目 | 第 6 版 蒜薹:61kcal / P2.0 / F0.1,按 4P+4C+9F 反推可利用碳水约 13.0g,加膳食纤维约 2.5g |
| 牛腩 | F**24.0** | F**29.3** | 脂肪抄错 | 中国食物成分表 牛肉(腹部肉)【牛腩】编号 08-2-116:332kcal / P17.1 / F29.3 / C0 / 食部100% / 水分57.6g |

**关于牛腩的补充说明**:v1 只指出"332kcal 与宏量加总 284 不一致,需确认是能量偏高还是脂肪偏高",**结论是脂肪偏低**(24.0→29.3),项目方向判断正确。核对到该条目水分 57.6g + 灰分 1.0g + 蛋白 17.1g + 脂肪 29.3g ≈ 105%(取整误差),且饱和 14.7 + 单不饱和 13.3 + 多不饱和 0.3 = 28.3g 与总脂肪 29.3g 自洽,可确认为真实条目值而非按能量反填。

**关于鸡胸命名(接受评审修正)**:v1 建议改名"(去皮)"是错的 —— 官方条目名为"鸡胸脯肉",其脂肪 5.0g 介于 USDA 去皮(2.6g)与含皮(8~9g)之间,**无法据此断定部位口径**,改名等于用一个未核实断言替换另一个。名称保持"鸡胸肉"正确。

这里保留下 v1 中站得住的那半句原则:**这一行的真问题是"跨来源缝合"**,无论叫什么名字都不能保留 `133kcal(中国表,含 5g 脂肪) + 22g 蛋白(去皮口径)` 的组合。正确做法是全行统一到同一来源,二选一:

- **① 全用第 6 版**:133 / P19.4 / C2.5 / F5.0,名称"鸡胸肉" —— 项目已采用,与全库基准一致 ✅
- ② 全用 USDA 去皮生鸡胸:120 / P22.5 / C0 / F2.6,名称"鸡胸肉(去皮)" —— 需同时改 kcal 与 verify 断言,且全库仅此条用 USDA 会破坏基准一致性(不推荐)

**顺带观察(非错误)**:库内命名粒度不统一 —— `f_chicken_leg`「鸡腿肉(去皮)」、`f_duck_breast`「鸭胸肉(去皮)」带部位限定,而 `f_chicken_breast`「鸡胸肉」不带。建议统一规则:**命名以来源条目名为准**(官方叫什么就写什么),而不是按推断补部位限定。

### 2.2 自洽性闸门:采纳 -12%,但需要理解它的新角色

**v1 的理论错误(已接受)**:我提出"膳食纤维只会把 `4P+4C+9F` 推高、不可能推低,所以负偏差必为错,阈值可取 -5%"。这个推论只考虑了纤维,漏掉了另外两个因素:

1. **Atwater 系数与实测能量的偏差**:脂肪实际代谢能约 8.9 kcal/g、蛋白约 4.0~4.1,高脂食材用 9 会系统性偏高一点;
2. **低能量/高水分食材的小分母放大**:能量基数越小,同样 1~2g 的取整误差造成百分比越大。

项目方给出的 4 个反例**全部复核准确**:

| 食材 | 标注 | 4P+4C+9F | 偏差 |
|---|---|---|---|
| 北豆腐 | 116 | 104 | **-10.3%** |
| 鸡翅 | 194 | 182 | -6.3% |
| 三文鱼 | 180 | 170 | -5.6% |
| 鸭胸肉(去皮) | 133 | 126 | -5.3% |

`-5%` 会让 verify 永久红 4 条正确数据,不可行。**实际实施的 `dev < -0.12 || dev > 0.5` 是合理的**(`verify.mjs:64`)。

**但 v2 要补三点,否则这个闸门的价值会被高估**:

1. **修完数据后,这条闸门当前抓不到任何东西。** 复跑全库负偏差分布:最差是北豆腐 -10.3%,`[-20%, -12%]` 区间 **0 条**。牛腩(-14%)、蒜薹(-33%)都已修好。所以它的角色已经从"抓本次真错"变成**"防未来回归"**。它的验收标准也应随之改变:不是"当前有 N 条命中",而是**故意注入一条 -15% 的错误数据能被抓到**(故障注入测试)。
2. **余量只有 1.7 个百分点。** 北豆腐是真实的第 6 版数据(116 / P12.2 / C3.0 / F4.8),它距离 -12% 闸门仅 1.7pp。任何一次官方值微调或取整规则变化都可能让它永久变红。若要稳一点,可做**双档**:硬失败 `-15%`(专捉数量级错误)+ 软警告 `-10%`(打印清单人工过目,当前预期为北豆腐一行)。这样把"必须为 0"和"需要人看"分开,verify 的失败语义更准确。
3. **这个指标本身是弱判别器,别让它承担过多。** 实测:合法数据下限 -10.3%,最小真实抄错 -14%,两者只差 3.7pp。**单靠百分比无法可靠区分"合法但偏差大"和"抄错一位"**。真正的把关应该是溯源元数据(下条)。

**已落地的更好做法(值得肯定)**:v0.16.3 在 `verify.mjs` 里加了**数据锚点断言**,直接锁死具体值,比启发式百分比可靠得多:

```js
check('燕麦片 50g ≈ 191kcal(381/100g)', ...)
check('蒜薹 150g 碳水 ≈ 23.1g(总碳水15.4,曾误用蒜苗的8.0)', ...)
check('牛腩脂肪 = 29.3g(与 332kcal 自洽,曾误抄 24.0)', ...)
```

建议对**所有高杠杆条目**(鸡胸、米饭、燕麦、蛋、奶、油、常用蛋白源)都加这类锚点,覆盖 20~30 条即可把"数据被改坏"的风险压到很低。

### 2.3 数据溯源元数据(建议新增)

现有 `foods.js` 头部已改为"以《中国食物成分表 标准版》第 6 版为基准(经中国疾控中心营养与健康所食物营养成分查询平台逐条核对)"。但**并非每行都真出自第 6 版** —— 例如牛腩的官方出处是"牛肉(腹部肉)【牛腩】编号 08-2-116",可追溯到 2002/2004/2009 版收录,第 6 版是否以"牛腩"为条目名待确认。

建议对高杠杆条目加条目号注释:

```diff
-  { id: 'f_beef_brisket', name: '牛腩', category: 'meat', kcal: 332, protein: 17.1, carbs: 0, fat: 29.3 },
+  // 中国食物成分表 牛肉(腹部肉)【牛腩】编号 08-2-116,食部100%,水分57.6g
+  { id: 'f_beef_brisket', name: '牛腩', category: 'meat', kcal: 332, protein: 17.1, carbs: 0, fat: 29.3 },
```

有了条目号,评审与维护就能逐条回溯,不必依赖"4P+4C+9F 百分比"这种弱信号 —— 这是本节的根治方案。同时建议把头部措辞从"第 6 版为基准"改为"以《中国食物成分表》各版本为基准,高杠杆条目注明条目号",使声明与事实一致。

### 2.4 其余 30 条正偏差:无需处理

全库 153 条食材中,`4P+4C+9F` 高于标注热量 10% 以上的有 30 条(彩椒 +30%、平菇 +43%、魔芋结 +46%、空心菜 +30%、圣女果 +32% 等),**均为蔬菜/菌菇/水果,由膳食纤维计入碳水造成,属正常**,不动。

### 2.6 🔶 部分修复:抗炎标签

v0.16.3 已按建议改为**油类不计入"抗炎食材种数"**。复检结果:

### 2.7 ⬜ 未修:生重 / 熟重提示

数据统一用生/干重(名称带"(生)/(干)",这点做得对)。但 UI 只显示"大米(生) 70g",减脂新手容易按"一碗熟饭"理解 —— 100g 熟米饭 116 kcal,100g 生米 346 kcal,差 3 倍。建议:① 食材行加"生重"角标;② 主食槽附常用熟重换算(如"≈160g 熟饭")。

### 2.8 其它数据观察(非错误)

- 三文鱼 180 kcal 是养殖(208)与野生(142)的中间值;**龙利鱼**市售多实为巴沙鱼;**豆浆** 31 kcal 对应浓豆浆(官方条目 14 kcal)。这类天然波动大的条目,建议在名称里加限定(如"三文鱼(养殖)"),而不是给折中值。
- **红薯**存疑未决:项目 90 kcal / C21.3;中国疾控中心平台"甘薯(红心)"为 432kJ≈103 kcal / C24.7(食部 90%),另有数据库给 61 kcal / C15.3。**公开来源本身分歧大,不作"错误"判定**,建议统一到官网口径并注明版本。

1. **事实错误** —— v1 写"`/week` 已有重定向占位,可复用"。事实是 `git log` 显示 `v0.2.0 feat: 周计划与采购清单…` 引入该功能,而 v0.13/v0.14 转"记录型用户"时**主动砍掉了周计划页**(当时理由:做饭频率低、采购清单价值低)。我把一次"产品收敛的产物"读成了"预留的占位",这是无依据的意图推断 —— 恰与我在同一份文档里批评数据层"用未核实断言替换另一个"属同类行为。
2. **优先级错误** —— 把它列 P0 且称"投产比最高",等于替产品决策排序。

**修正后的判据(v2 采纳)**:在"主动砍掉"的语境下,**保留纯函数内核、不接 UI 恰恰是低成本高可选的正确做法**(内核纯函数零依赖,恢复成本几乎为零)。因此**"有内核无 UI"本身不是缺陷信号**。正确的缺口判据是:**功能同时具备内核 + UI 入口,而入口被破坏/隐藏时**才算缺口。单有内核时,必须先确认产品意图,不能自动判定为洞。

**残留的站得住的项**:无。v0.16.3 已删除 `makeBaselineItem` 死代码 ✅。

**待决策的取舍(不替产品拍板)**

## 4. 逻辑性缺陷

### 4.1 ✅ 已修:跨零点记录写到昨天

原状:`const today = todayStr()` 在 `TodayView` / `AddRecipePopup` 的 `setup()` 里只取一次,页面挂过夜后记录写到昨天。v0.16.3 新增 `src/composables/useToday.js` 并在 `TodayView` / `RecordView` / `AddRecipePopup` 全部接入 ✅("跨零点自愈")。

### 4.2 🔶 已清理语义,v2 重新定性

**修正定性**:`summarizeDay` 不排除 skip **不是无意分叉**,而是 v0.7 时代为周计划页保留的"计划口径" —— 周计划页删除后语义悬空。v0.16.3 已把口径下沉统一 ✅。

**一条支持该历史解释的代码佐证**:`summarizeDay(dayPlan, foods, targets)` 的签名接收 `{ date, meals }` 普通对象、不去 store 里查,恰好匹配 `generateWeekPlan` 的产物结构 —— 说明它从设计上就是为周计划流水线服务的,与"计划口径"的解释自洽,不是事后合理化。

**v2 的改进建议**:既然原语义是"计划口径",把它统一成"摄入口径(排除 skip)"其实是**改变语义**,不是"修正错误"。若周计划将来恢复,该需求会再次出现。建议**不要合并成一个函数**,而是两个命名明确的函数:

```js
summarizePlanned(dayPlan, foods, targets)  // 计划口径:含被跳过的餐
summarizeIntake(dayPlan, foods, targets)   // 摄入口径:排除 skip
```

或至少在函数名/注释里把口径写死,否则恢复周计划时会再踩一遍。

**风险重新定级**:v1 称其为"定时炸弹/bug" → 降为**"命名与注释缺失的可维护性问题"**。v1 说"同一份数据能算出两个不同的全天热量"技术上仍成立,但它没有展示出口,不构成用户可见缺陷。

### 4.3 ✅ 已修:`swapSlotItem` 死参数与硬编码

原状:`usedIds` 参数从未使用;换主食固定按 45% 热量倒推。v0.16.3 已激活 `usedIds` 过滤并新增 `stapleKcal` 参数按该餐剩余热量缩放 ✅。

### 4.4 🔶 已加提示,增长问题仍在

v0.16.3: `storage.js` 捕获 `QuotaExceededError`/`code 22` 并节流提示(30s)✅;`week.js` 新增 `pruneStaleEmptyDays` 清理 180 天前**生成过但无任何菜品**的空天 ✅。

两点补充:
1. **空间增长并未解决。** `pruneStaleEmptyDays` 只清"空天",而**有内容的天永不清理** —— 真正占空间的是后者。所以"配额满"的风险只是从"静默失败"变成"可见失败",并没有消除。长期方案:按天归档到 IndexedDB,或提供"导出后清理 N 年前记录"。
2. 治理策略**偏向保守是对的**(宁可不清也不误删),这一点做得好。

## 8. 评审方法与局限

本节记录 v1 出错的机制,以及为降低重复概率而建议的机制改进。

### 8.1 v1 的 4 处错误分布

| 错误类型 | 次数 | 案例 |
|---|---|---|
| 无依据的意图/事实推断 | 1 | "`/week` 是预留占位"(实为主动砍掉的产物) |
| 理论推导漏项 | 1 | -5% 阈值漏掉 Atwater 偏差项 |
| 把历史语义缺失判定为 bug | 1 | `summarizeDay` 的"计划口径" |
| 越位替产品决策排序 | 1 | 周计划列 P0 |

**共性与数据层的错误同源**:用未核实的推断替换事实。评审代码时,"看起来缺什么"和"实际缺什么"之间隔着产品意图与决策历史。

### 8.2 机制建议

1. **把产品决策落进仓库**(最重要)。当前 32 个提交的信息全部只在 commit message 里,没有 CHANGELOG、没有 `docs/decisions/`、没有 ADR。结果:任何代码考古(人或其他评审者)都无法区分"刻意不做"与"忘了做",v1 的误判几乎是必然的。
   建议:① 新增 `CHANGELOG.md`,按版本记录"做了什么 + 为什么";② 对砍功能类的决策(如 v0.13 砍周计划页),在 `docs/decisions/` 留一条简短记录,或至少在代码里留一行注释。
2. **评审范围写进文档**。v1 声称评估"功能完善性",但实际只评估了"代码可见的功能完整性"。二者差别正是本次出错的区域。
3. **结论分级标注**。v1 把"事实"和"推断"混在同一个语气里(如 §3.1 的"占位可复用")。建议评审文档对每条判断标注来源:【代码事实】/【推断,需确认】/【产品决策,待定】,让可被反驳的部分显式暴露。

### 8.3 对评审结论本身的态度

v1 中"代码事实"层面的发现(数据错误、死参数、跨零点、汇总口径、可食部口径)经复核全部成立,并已被 v0.16.3 采纳;错误集中在"意图与优先级"层面。因此:**对代码事实类的发现可以按建议实施;对意图与产品方向类的判断,应先与决策方确认再执行。**
