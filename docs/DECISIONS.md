# cookbook 决策记录(为什么"没做"/"这么做")

只记**被主动否决的方案与有意的取舍**及理由——"做了什么"考古看 git log,
"为什么没做"在这里。评审多轮反复争论的点(周计划 UI、鸡胸命名、闸门阈值)
最终以本文件为准,不再重提。

## 产品形态

- **纯前端本地应用,无后端、不调用外部 API**(立项三轮澄清):数据存
  localStorage + 导出/导入 JSON;OCR 用本地 Tesseract.js(语言包 CDN 按需加载,
  自托管是候选优化项)。云端识菜、云端多模态 API 均因本地原则被否。
- **记录型而非规划型**(v0.13/v0.14):用户做饭频率低、饮食单一,产品重心是
  "记录实际 + 对照目标",不是"生成计划照着吃"。后续迭代默认此画像。
- **训练日/休息日分化**:未采纳(立项澄清,未提出即不预设)。
- **增肌模式不做"预计到目标日"预测**(v0.18.0):热量盈余在肌肉/脂肪间的分区
  个体差异大,按 7700kcal/kg 推算到日是假精确;只显示周增速对照建议区间
  (+0.25~0.5kg/周)。维持模式无进度概念,进度块整块不渲染。
- **真 App(安卓套壳 / iOS)缓做**(v0.20.0 讨论后判):PWA 已覆盖桌面图标/
  全屏/离线需求;iOS 需 $99/年开发者账号 + Mac,对单人自用不成比例;安卓
  Capacitor 套壳的 localStorage 与浏览器版不互通(两套数据),反而添负担。
  恢复判据:部署后实际使用一两周,仍觉得"必须是独立 App"再做。
- **OCR 语言包离线不可用**(v0.20.0 已知取舍):语言包走 CDN(跨域),SW 不缓存;
  离线时拍照导入退化为手动录入,核心记录功能不受影响。自托管语言包仍是
  独立候选轮次。

## 砍掉/撤下的功能

- **周计划页 + 采购清单 UI**(v0.13/v0.14 主动砍掉,`0a28390`/`3e50917`):
  记录型定位下采购清单价值低。`generateWeekPlan`/`buildShoppingList` 纯函数
  保留且 verify 覆盖,恢复只需接 UI。恢复判据:重新出现"周末集中采买"诉求。
- **生成带"最近吃过"独占偏好**(v0.16.1 推翻 v0.14.0):单调饮食者每次重新
  生成都会复现同一批菜,且生成结果写回当天又进下次偏好池,自我强化。
  "熟悉"的入口 = 添加弹层的"最近吃过"chips。planner 纯函数 recentIds 契约
  保留,供将来"常吃优先"开关复用(verify 固化其行为)。
- **设置页导入/导出**(v0.9.0 删):当时判断价值低;v0.15.0 以"数据管理"
  形态恢复(导出全部 `cookbook:*` key + 导入覆盖确认)。

## 数据口径

- **克数 = 市场购买量,营养按 edible 食部折算**(v0.17.0,评审方案 A):
  否掉"按可食部克数记账"——用户要在"买 300g 蛤蜊/记 120g"间换算,记录成本高。
  edible 只标壳/骨/棒类结构性浪费且官方可查的 7 条;薯类表皮等 ~10% 食部差
  **未建模**(土豆/山药/芋头/南瓜等同此粗口径,要改需全类逐条核实官方食部)。
  牡蛎官方条目按蚝肉计(食部 100%)不标。
- **名称限定词只标注官方条目可核实的口径**:"鸡胸肉"不加"(去皮)"——官方
  鸡胸脯条目脂肪 5.0 介于 USDA 去皮 2.6/含皮 8-9 之间,无法断定部位口径,
  不断定则不加(v0.16.3)。同理"牛腩/猪肋排/兔肉"不带"(瘦)"。
- **红薯 = 第6版红心甘薯 103kcal/C24.7**(v0.17.1):曾用 90/21.3 无出处
  (介于 USDA 生薯与官方之间)。官方"甘薯(红心)"别名即"红薯"
  (432kJ、P1.1、C24.7、F0.2、食部 90%);评审 v3 引用的"红心 61kcal/C15.3"
  经官方平台核实不成立(水分 73.4g 下 24.7g 碳水不可能只有 61kcal)。
- **自洽闸门 -12% / +50%**(v0.16.3):负向取 -12% 因高水分/高脂官方条目
  Atwater 加总天然偏低 3~10%(北豆腐 -10.3%),评审批评时建议的 -5% 会误伤;
  正向 +50% 容忍魔芋结(+46%)/平菇(+43%)等高纤维条目——碳水以葡甘聚糖等
  近零供能纤维为主,4kcal/g 加总系统性高估,属预期不是错。闸门角色是**防回归**,
  当下抓错靠数据锚点断言,不靠"跑一遍看红"。
- **天然波动条目不强改单值**(三文鱼养殖/野生、龙利鱼实为巴沙鱼、豆浆浓度、
  茅屋奶酪品牌差):取典型市售值,改"唯一正确值"是把诚实的近似换成不诚实的
  确定值(与鸡胸命名同理)。

## 算法取舍

- **主食槽 300g 上限 + 真实交付口径**(v0.16.2):防低热量密度主食(芋头/南瓜)
  按剩余热量倒推时体积爆炸;选择判据用 scaleRecipe 截断后的实算交付量,理论值
  会"假合格"。代价:极端画像偏差 ±1% → ±3~5%,已知并接受。
- **蛋白槽 85% 蛋白目标 + 45% 热量上限,合格池 90% 交付**:设计参数,自检容差
  (蛋白 -10%~+40%)与之配套。
- **蔬菜槽 100g 主料门槛**(v0.16.3):紫菜汤类点缀不占蔬菜槽;手动添加不受限。
- **抗炎派生:油类不计"种数"**(v0.16.3):≥2 种非油抗炎主料或 ≥80g 非油
  抗炎主料才标食谱,否则"任何带油的菜都算抗炎"。
- **体重半动态:近 7 天均值每满 2kg 调一档,朝档案体重保守**(v0.16.0):
  每日动态无意义——体重系数约 10kcal/kg,1kg 体重 ≈ 12-16kcal/天 TDEE,
  远小于饮食记录误差;阶梯化避免逐日噪音。
- **自定义食物不进组装池/采购清单**(v0.8.0):独立层与种子库隔离,典型场景
  是已购单品。
- **排除组合边界**(v0.17.1 记录):全部排除标签的单/双组合下每餐每槽位仍有
  候选(verify 断言固化);egg+milk+soy 三排时早餐蛋白槽为 0 是已知边界——
  纯素用户,补候选需新增食谱(内容扩充,待真实诉求出现再做),页面空态文案
  会指引用户调整排除设置。
- **食材频次约束(weeklyLimit)口径**(v0.19.0):按"近 7 天出现过的天数"计,
  同天多餐算 1 天,生成与手动记录同口径(健康暴露只看事实)。生成/换菜端硬规避
  且不参与池空回退(宁空槽不超限);手动添加走确认层软提示不阻断(自己负责)。
  已知语义:重新生成某天时,被弃的旧计划也计入 7 天窗口(方向保守,只多避不少避,
  评审 v4 F-3.3);天内三餐共用一份计数、不累计,受限食材(猪肝/金枪鱼罐头)各
  仅 1 个食谱引用,同天双选当前构造不出来,入第 2 个食谱前需先补天内累计
  (评审 v4 F-3.1);鸡肝 weeklyLimit 为前瞻配置,暂无食谱引用(评审 v4 F-3.2)。

## 存储与持久化

- **有内容的天永不清理**(v0.16.3):pruneStaleEmptyDays 只清 180 天前的空天。
  知情的取舍:配额满有 toast 提示 + 导出备份兜底;粗估 5 年约 2~3MB,逼近
  localStorage 上限再做归档(只留日期+总计)。
- **存量数据不做口径迁移**(v0.17.0 起的一致原则):数据口径修正后,历史记录
  的营养按新口径重算(更接近真实),与记录当时显示值不同属预期。
