## 1. 新发现

### F-1【代码事实,中】换菜的"避开全库已出现食谱"从未生效 —— `usedIds` 恒为空集合

`src/stores/week.js` `swap()`:

```js
const usedIds = new Set(
  Object.values(this.days)
    .flat()
    .filter(Boolean)
    .map((it) => it.recipeId)
)
```

`Object.values(this.days)` 的元素是 **meals 对象**(`{breakfast:[],lunch:[],dinner:[]}`),
不是数组;`.flat()` 只展开嵌套数组,对普通对象无效。实测该表达式结果为
`Set([undefined])`——任何食谱 id 都进不了 usedIds。

- **影响**:换菜时"尽量避开吃过的食谱、池子耗尽才回退"这一层实际从不生效,
  每次换菜都在第一候选池(仅排除当前食谱)里随机。**不是正确性错误**(换入的菜合法、
  缩放正确),是多样性降级;也解释了为什么无人报障——表现只是"换菜可能换回刚吃过的菜"。
- **为何此前未抓到**:verify §21 的换菜断言直接向纯函数 `swapSlotItem` 传
  `usedIds: new Set(['x_s2'])`,绕过了 store 组装层;store 层无测试覆盖。
- **修复建议**(diff 片段,待确认后执行):
  ```js
  const usedIds = new Set(
    Object.values(this.days)
      .flatMap((m) => Object.values(m || {}))
      .flat()
      .filter(Boolean)
      .map((it) => it.recipeId)
  )
  ```
- **配套建议**:把"从 days 提取已用食谱 id"下沉为 planner.js 的纯函数(如
  `collectUsedRecipeIds(days)`),verify 直接测它,堵上"store 组装层不可测"的结构性盲区。

### F-2【代码事实,中】蛋白槽候选打分用理论值且隐含 s≤1,与主食槽"真实交付口径"不一致

`planner.js assembleMeal` 蛋白槽打分:

```js
const deliverable = base.kcal > 0
  ? Math.min(proteinWant, base.protein * Math.min(1, proteinMaxKcal / base.kcal))
  : 0
```

`Math.min(1, ...)` 意味着**打分假设缩放系数最大为 1**——忽略了 `scaleRecipe` 实际允许
s 到 3、也忽略克数钳制/单位吸附。而 v0.16.2 已为主食槽确立"选择判据必须用真实交付量"
(`realDeliverable`),蛋白槽没有跟进,同文件内两套判据并存。

实测(早餐蛋白目标 30g、want=25.5g,脚本逐候选回算):

| 候选 | 理论 deliverable | 真实可交付 | 结果 |
|---|---|---|---|
| 水煮蛋白 | 23.2 | 25.5 | 唯一"合格" |
| 蒸蛋羹 | 20.3 | **28.7** | 实际达标却被排除出合格池 |
| 茅屋奶酪碗 | 18.0 | **25.6** | 同上 |
| 豆腐脑 | 15.0 | 22.5 | 被低估 |

- **影响**:① 合格池系统性偏小,高蛋白目标(如午餐 40g+)下几乎必然落入
  top-5 兜底,而兜底排序按"基准蛋白"而非真实交付,偏向高密度肉蛋,奶/豆制品
  即使能缩放达标也排不进前列——**多样性损失**,最终交付数字本身仍是正确的
  (缩放由 scaleRecipe 完成)。② 与 F-1 不同,这条不改结果正确性,改的是"选谁"。
- **修复建议**:`realDeliverable` 扩展支持 `maxKcal` 透传(它内部调 `scaleRecipe`
  时不传 `maxKcal`),蛋白槽打分改走真实交付。改动集中在 assembleMeal 一处,
  配合既有 §生成断言即可回归。

### F-3【代码事实,中】清炖狮子头含 30g 鸡蛋白,未标 `egg` —— 排除"蛋"后仍会入池

`r_lions_head_meatball` 配料含 `{ foodId: 'f_egg_white', grams: 30 }`,`tags: ['pork']`
缺 `'egg'`。排除标签是**过敏/忌口语义**,排除蛋的用户仍会被生成/换菜推荐含蛋白的菜——
方向是"泄漏",比 F-4 的"误伤"严重。全库双向扫描(52 食材映射)仅此 1 处缺标。

- **结构性问题**:verify 的排除测试是"带某标签的食谱不应出现在排除后的候选里"——
  它测的是过滤机制,**机制永远正确,缺标永远抓不到**。标签与食材的一致性需要
  独立断言。
- **修复建议**:① 补标 `egg`;② 在 verify 加"食材→标签一致性"断言(本轮扫描脚本
  即原型,可把 FOOD_TAG 映射固化为 seeds 的一部分),以后新增食谱漏标直接红。

### F-4【代码事实,低】凉拌鹰嘴豆误标 `soy` —— 且它是三排边界空槽的成因

鹰嘴豆不是大豆,`r_chickpea_salad` 配料(鹰嘴豆+橄榄油)不含任何大豆成分,
`tags: ['soy']` 系误标。排除"豆制品"的用户被误伤一道合规菜。

- **附带发现**:DECISIONS 登记的"egg+milk+soy 三排时早餐蛋白槽为 0"这一已知边界,
  实际由本误标直接造成——早餐蛋白槽的素食候选(豆腐脑/豆浆/黑豆浆)全是真大豆制品,
  唯一非大豆的鹰嘴豆被误标顶掉。**修正标签后该边界自动从 0 变为 1**。
- **修复建议**:摘除 `soy` 标,同步更新 DECISIONS 边界条目的表述;§23 排除组合断言
  的期望值需随之重跑确认。
